# pi-session-inspector — Reporting Guide

`pi-session-inspector` scans Pi agent session logs and reports token consumption and
pricing. This page documents every reporting mode and shows working command-line
examples.

```
Usage: pi-session-inspector [OPTIONS]
```

Run `pi-session-inspector --help` anytime for the concise built-in help.

---

## 1. The session data model

Each Pi session is a `.jsonl` file under `~/.pi/agent/sessions/<project-folder>/`.
A single session file contains one or more model exchanges ("calls"). The tool
aggregates usage across calls and exposes these per-session statistics:

| Statistic | Meaning |
|---|---|
| `input_tokens` | Non-cached prompt (input) tokens sent to the model |
| `cached_input_tokens` | Input tokens served from cache (`cache_read + cache_write`) |
| `output_tokens` | Completion (output) tokens generated by the model |
| `reasoning_tokens` | Thinking/reasoning tokens (billed as output for deepseek; may be 0 on providers that don't report them) |
| `total_tokens` | `input + cached + output` across all calls |
| `duration` | Wall-clock time from session start to its last message |
| `turns` | Number of user messages (conversation turns) |
| `price` / `cost` | Dollar cost of all usage |
| `cost_input` / `cost_output` / `cost_cached` | Price broken down by billing component (see Mode B) |
| `messages` / `calls` | Message and assistant-call counts |
| `cache_invalidations` | Times the prompt cache was invalidated (cache hit → full miss transition), shown in `-d` detail and CSV |
| `cache_lost_tokens` | Input tokens lost to cache invalidation (previously-cached tokens re-processed at full price) |
| `cache_lost_cost` | Dollar cost of that loss: lost tokens × (effective full-input rate − effective cache rate) |
| `context_tokens_at_end` | Total context size (`input + cache_read`) sent to the model on the **final** assistant request — the context in use at the end of the session |
| `tool_breakdown` | Per-tool call counts + produced output/reasoning tokens (Mode D) |

## 2. Selecting what to report

You can narrow the scan by several selectors. All values are **regex** patterns
except `--provider` / `--model`, which use case-insensitive substring match.

| Flag | Selects by | Example value |
|---|---|---|
| `-p, --project` | Project working directory (`cwd`) | `firstmate.*rm` |
| `-N, --name` | Named session<br/>(from the session's `session_info` name) | `^implementation` |
| `-S, --session-path` | Session file path<br/>(includes the project folder) | `firstmate.*2026-08-07` |
| `-P, --provider` | Provider, e.g. `openai-codex`, `anthropic` | `deepseek` |
| `-m, --model` | Model id, e.g. `gpt-5.6-sol` | `DeepSeek-V4` |

Selectors can be combined — filters stack (AND).

### Listing modes (discover what's available, then exit)

| Flag | Prints |
|---|---|
| `--list-names` | All distinct named sessions (use `-N` to filter the list) |
| `--list-projects` | All distinct project paths (use `-p` to filter the list) |
| `--list-session-paths` | All session file paths (use `-S` to filter the list) |

## 3. Reporting modes

The output format is controlled by `-f, --format` (`table` or `csv`), and the amount
of detail by `-d / -M / -R / -T`.

### Mode A — Summary table (default)

Columnar overview of all matched sessions plus a grand total.

```bash
pi-session-inspector
```

```
Idx    Date                  Project / Name                           Input   CachedIn    Output  Duration      Tokens   Cost ($)
------------------------------------------------------------------------------------------------------------------------------------
1      2026-08-25 14:45      ~/llm/pi-usage-deepseek-pro              33.0K     329.7K     11.6K    5m 31s      374.4K  $0.010013
------------------------------------------------------------------------------------------------------------------------------------
Total: 1 sessions, 40 messages, 20 assistant calls (33.0K in / 329.7K cached / 11.6K out)              374.4K  $0.010013
```

> Tip: combine with any selector to see matching rows, e.g.
> `pi-session-inspector -N semipermeable`.

### Mode B — Detail (`-d`)

Per-session deep dive: id, file, project, name, turns, duration, input / cached /
output / reasoning / total tokens, a **price breakdown** (cost split into input,
cached, and output with effective per-million rates, plus an estimated reasoning
share), a per-model breakdown, and a **per-tool breakdown** of which tools were
called and how much output/reasoning each produced.

```bash
pi-session-inspector -N '^debug$' -d
```

```
── Session 1 ──
  ID:       019fdd17-2225-76ae-bb68-9da8b14336bb
  File:     /home/denis/.pi/agent/sessions/--home-denis-llm-firstmate-rm--/2026-08-07T16-38-28-645Z_....jsonl
  Project:  /home/denis/llm/firstmate-rm
  Started:  2026-08-07T16:38:28.645Z
  Name:     implementation-deepseek-v4-flash-minimal
  Messages: 402 (22 user, 193 assistant, 187 tool results)
  Turns:    22
  Duration: 3h 08m 36s
  Cache invalidations: 3 (250.0K, $0.002000)
  Context at end of session: 420.0K
  Tokens:
    Input tokens:              3.4M
    Cached input:             26.3M
    Output tokens:           102.2K
    Reasoning tokens:            0
    Total:                    29.8M
  Cost (price breakdown):
    Input:        $0.023085       (@ 0.0800/M)
    Cached:       $0.438104       (@ 0.0160/M)
    Output:       $0.024433       (@ 0.1800/M)
    Total:        $0.485622
  Models:
    deepseek-ai/DeepSeek-V4-Flash-0731      29.8M  $0.796547  ( 193 calls)   in 3.4M / cached 26.3M / out 102.2K / reasoning 0
```

The `-d` price breakdown shows **why** a session cost what it did:

- Each component (`Input` / `Cached` / `Output`) is listed with its **effective
  per-million rate** (e.g. `@ 0.6600/M`), so you can see e.g. that cached input is
  the dominant volume but billed at a low rate, whereas output/reasoning tokens
  carry a high rate.
- If the session has reasoning tokens, an extra line estimates the reasoning share
  of the output cost (`reasoning` is billed as `output` on deepseek) proportional
  to its token share.

### Mode C — Provider / Model rollups (`-R`, `-M`)

Append aggregate provider or model breakdowns to the report (across all matched
sessions):

```bash
pi-session-inspector -R -M
pi-session-inspector -R       # providers only
pi-session-inspector -M       # models only
```

```
Model breakdown:
Model                                    Tokens          Cost ($)    Calls
--------------------------------------------------------------------------
deepseek-ai/DeepSeek-V4-Flash-0731        ...             ...        ...
```

`-R` and `-M` can be combined with `-d` to get both the aggregate rollup and the
per-session detail.

### Mode D — Tool breakdown (`-T`, `--per-tool`)

Append a per-tool breakdown (across all matched sessions) that shows how many
times each tool was called and how many output/reasoning tokens the model
produced to issue those calls:

```bash
pi-session-inspector -T
pi-session-inspector -T -d   # also print each session's own tool breakdown
```

```
Tool breakdown (all sessions):
Tool                               Calls       Output    Reasoning     Out+Reas
--------------------------------------------------------------------------------
bash                                 447       273.9K       101.7K       375.6K
edit                                  36        46.6K        21.1K        67.7K
write                                 18        56.3K         5.2K        61.5K
...
```

Attribution rules (kept deliberately simple and reliable):
- `Output` / `Reasoning` are the tokens the model generated to issue each tool
  call, computed by **evenly splitting** each assistant turn's `output` across the
  tool calls made in that turn (any integer-division remainder goes to the first
  call so the per-tool totals exactly match the session totals).
- **Consumed/input tokens are intentionally NOT attributed per tool** — input
  deltas don't map cleanly to individual tool results (they include cache-miss
  re-reads, prompt context, etc.), so attributing them would be misleading.
  Use the tool's `Calls` column as the accurate measure of consumption.

The same breakdown is shown per-session in `-d` detail mode, and added as a
`tool_breakdown` column in CSV with `-T -f csv`.

### Mode E — CSV export (`-f csv`)

Machine-readable output with one row per session. Extend with `-R` / `-M` / `-T`
to add provider / `model_breakdown` / `tool_breakdown` columns.

```bash
pi-session-inspector -N '^debug$' -f csv
pi-session-inspector -f csv -M -R > report.csv
```

```
index,session_id,file,cwd,display_name,started_at,total_tokens,total_cost,input_tokens,cached_input_tokens,output_tokens,duration_secs,turns,message_count,...
```

## 4. Ordering and limiting

| Flag | Behavior |
|---|---|
| `-s, --sort <KEY>` | `token-desc`, `token-asc`, `cost-desc`, `cost-asc`, `date-desc`, `date-asc` (default `date-desc`) |
| `-n, --limit <N>` | Keep only the top N sessions after filtering/sorting |

```bash
# Top 10 most expensive sessions
pi-session-inspector -s cost-desc -n 10

# 5 most token-hungry sessions in a given project
pi-session-inspector -p 'firstmate.*rm' -s token-desc -n 5

# Oldest sessions first
pi-session-inspector -s date-asc
```

## 5. Other options

| Flag | Behavior |
|---|---|
| `--sessions-dir <PATH>` | Override the sessions directory (default `~/.pi/agent/sessions`) |
| `--html <PATH>` | Write a self-contained HTML report to `<PATH>` for the matched session(s), then exit |
| `--json <PATH>` | Write the report data model (the same data the HTML report embeds) as JSON to `<PATH>`, then exit |
| `-h, --help` | Print help |
| `-V, --version` | Print version |

### HTML report (`--html <PATH>`)

Generates a single self-contained HTML file (no network/CDN needed — open it
straight from disk) for the session(s) selected by the usual filters. Combine it
with `-S` (session path) to target one file:

```bash
pi-session-inspector --html /tmp/report.html -S 'rm-otel-dash-v2'
```

The page is built for finding **problematic requests** — the ones that sent a
lot of fresh (non-cached) input tokens or that **invalidated the prompt cache**:

* **Histogram** — one bar per assistant request, sized by that request's fresh
  `input` tokens (log scale). Bars are colour-coded:
  * **amber** = large input (above an adaptive per-session threshold),
  * **red** = this request lost the cache (a red marker below the bar also
    pinpoints the exact spot).
* **Click-to-focus** — hovering a bar shows the exact figures; clicking a bar or
  a red cache-loss marker scrolls to and flashes that request in the timeline.
* **Timeline** — every assistant request in order, with its usage chips
  (input / cached / output / reasoning / total / cost), `thinking` block, any
  assistant text, and each tool call with its JSON arguments and results.
* **Large request** list (yellow) — the top-five largest-input requests, each as a one-click link (cache losses are shown separately by the cache-loss timeline).
* **Session stats** — totals plus cache-loss counter, lost tokens and their cost, and the **context used at the end of the session** (the total context, `input + cached`, on the final request).
* **Context at end** stat in each session's overview and index line shows how big the model's context had grown by the session's last request.

`--html` writes one `<section>` per matched session, so you can aggregate several
sessions into a single report:

```bash
pi-session-inspector --html /tmp/both.html -S 'rm-otel-dash-v[28]'
```

### JSON report (`--json <PATH>`)

Writes the exact data model the HTML page embeds, so terminal front-ends can
render the same information without scraping HTML:

```bash
pi-session-inspector --json /tmp/report.json -S 'rm-otel-dash-v2'
```

The file has the shape `{"sessions": [ ... ]}`; each session carries the
aggregate stats (`input`, `cached`, `output`, `reasoning`, `total`, `cost`,
`invalidations`, `lostTokens`, `lostCost`, `contextEnd`, `durationSecs`, ...)
plus an ordered `requests` array with per-request usage, cache state
(`invalidated` / `lost`), `thinking`, `text` and `toolCalls` (arguments and
results). This is what the pi `/report-view` extension consumes to render the
report inside pi's TUI.

## 6. Full example walkthrough

```bash
# 1. What named sessions exist?
pi-session-inspector --list-names

# 2. Filter that list
pi-session-inspector --list-names -N 'impl.*'

# 3. Which projects did I work in?
pi-session-inspector --list-projects

# 4. Deep-dive one named session
pi-session-inspector -N '^debug$' -d

# 5. Everything for a project, aggregated by model
pi-session-inspector -p 'firstmate' -M -R -s cost-desc

# 6. Locate and inspect a single session file
pi-session-inspector --list-session-paths -S '2026-08-07'
pi-session-inspector -S 'firstmate.*2026-08-07' -d

# 7. Export to CSV for spreadsheets
pi-session-inspector -f csv -M -R > all_sessions.csv

# 8. See the per-tool breakdown (call counts + produced output/reasoning)
pi-session-inspector -T
pi-session-inspector -T -d -S 'otel-dash.*'   # per-session tool detail

# 9. Generate an HTML report to hunt for large-input / cache-loss requests
pi-session-inspector --html /tmp/rm-v2.html -S 'rm-otel-dash-v2'
```

## 7. Notes & caveats

- **Names vs paths:** `-N` matches the session's *name*; `-S` matches the *file path*.
  A name is not part of the file path (and vice-versa), so choose the selector that
  matches the identifier you know.
- **Regex semantics:** `--project`, `--name`, and `--session-path` are full regex
  patterns. Wrap them in quotes when they contain `*` or other shell-special
  characters. Invalid patterns fail fast with an error.
- **Cached input** = `cache_read + cache_write`; it is a separate component from
  `input`, not included in `input` sum.
- **Cache invalidations** counts the requests that fully missed the prompt cache
  (`cache_read == 0`) after a previous request had hit it — i.e. the cached prefix
  no longer matched and had to be rebuilt at full input price. Only requests that
  carry `usage` are considered. Note that some providers (e.g. deepinfra's
  DeepSeek) never populate `cache_write`; for them this hit→miss transition is the
  only observable invalidation signal.
- **Cache lost tokens** accompany each invalidation: the previously-cached tokens
  (the preceding request's `cache_read`) that dropped from the discounted cache
  rate down to full-price re-processing. Shown in `-d` as `Cache invalidations: N (X)`
  and in the `cache_lost_tokens` CSV column.
- **Cache lost cost** prices those lost tokens: the effective full-input rate minus
  the effective cache-read rate, both derived from the session's own totals
  (`cost_input/input` and `cost_cached/cached_input`), times the lost tokens. This
  is the extra money paid because the cache was invalidated rather than hit. It is
  exposed in `-d` (`Cache invalidations: N (X, $Y)`) and the `cache_lost_cost` CSV
  column, and it varies with the model: a lost Pro-cached request costs far more
  than a lost Flash-cached one.
- **Reasoning / price breakdown (`-d`)**: reasoning tokens are surfaced separately
  (deepseek reports them; many providers don't, so they read as `0`). Reasoning is
  billed as `output`, so the reasoning cost line in the `-d` breakdown is an
  **estimate** computed proportionally to its share of output tokens — it is not a
  separate line item in the raw usage.
- **`--list-*` modes** exit immediately and cannot be combined with `-d`, `-M`,
  `-R`, `-T`, `-n`, or `-f`.
- **Tool breakdown (`-T`) attribution**: `Output`/`Reasoning` per tool are produced
  tokens, evenly split across the tool calls in each turn (see Mode D). Consumed/
  input tokens are **not** attributed per tool — use the `Calls` count as the
  accurate measure of what each tool consumed.
